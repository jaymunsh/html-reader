## 공통 규약

### 명령

| 용도 | 명령 |
|---|---|
| 단위 테스트 | `npm test` (= `vitest run`), 단일 파일 `npx vitest run tests/unit/<name>.test.ts` |
| 타입 검사 | `npm run check` (= `svelte-check && tsc --noEmit`) |
| 빌드 | `npm run build` (agent → 앱), `npm run build:v2` (업데이트 테스트용 두 번째 빌드) |
| 픽스처 생성 | `npm run fixtures` (= `node scripts/make-fixtures.ts`, Node 26 타입 스트리핑) |
| E2E | `npm run e2e` (= `playwright test`), 단일 `npx playwright test tests/e2e/<name>.spec.ts --project=chromium` |
| 번들 예산 | `npm run size` (= `node scripts/check-size.mjs`) |

E2E는 항상 **프로덕션 빌드**를 `tests/server/static-server.mjs`로 띄워서 돌린다(dev 서버 사용 안 함). 이 서버는 `vercel.json`의 rewrite 두 개를 똑같이 흉내 낸다.

Playwright 프로젝트: `chromium`(Desktop Chrome), `webkit`(Desktop Safari), `mobile-chromium`(Pixel 7), `mobile-webkit`(iPhone 15), `update`(Chromium, 포트 4174, 직렬).
스펙 파일명에 `.desktop.`이 있으면 데스크톱 2개, `.mobile.`이 있으면 모바일 2개 프로젝트에서만 돈다. 그 외는 4개 모두.

### 식별자·경로 규칙

- book id: `^[a-z0-9]{12}$` (`newBookId()`), 캐시 이름 `book-<id>-v<n>`, 캐시 키 `cacheKey(bookId, path)` = `/book/<id>/` + 세그먼트별 `encodeURIComponent`.
- 앱 자산은 전부 `/__app/`, agent는 `/__reader/agent.js`, **SW 스크립트만 `/sw.js`**(스코프 `/` 확보용 — 스펙 공백, 아래 "스펙 이슈" 1번).
- SW ↔ 셸 메시지: `{type:'active-book', id: string|null}`, `{type:'book-changed', id}`, `{type:'skip-waiting'}`.
- 셸 ↔ agent 메시지는 `src/lib/protocol.ts`만 쓴다(P1 Task 18).

## 의도적으로 미룬 것 / 자동 검증하지 않는 것

- **실제 동영상 재생**: 픽스처 스크립트로 유효한 MP4를 만들 수 없어, 픽스처 7은 `fetch` Range 단언(206/416/suffix)과 스크립트로 생성 가능한 WAV `<audio>` 재생으로 검증한다. 실제 영상 재생은 README 수동 체크리스트(P4-3).
- **iOS 고유 동작**(상태바 실제 색, 홈 화면 앱 저장소 분리), **실제 설치 앱의 파일 연결·공유 시트**: 구현만 하고 README 체크리스트로 넘긴다(§11.3). 자동 테스트는 `launchQueue` 모의 객체와 폼 POST로 대체한다.
- **agent 단위 테스트**: agent는 DOM 의존이라 Vitest(node)로 다루지 않고 E2E로만 검증한다.
- **SW 유휴 종료 후 복구**: 브라우저에서 SW를 강제로 죽일 수 없어 자동화하지 않는다. 대신 SW가 모듈 전역 상태 없이도 동작하도록 P1-16/17에서 "메모는 캐시일 뿐"으로 구현한다.
- 시안 아티팩트(§13 링크)는 열 수 없어 §13 본문 값만 기준으로 삼았다. 픽셀 단위 일치 검수는 사용자가 한다.

## 스펙 이슈 (계획에서 임시 결정한 것 — 2026-11-13 사용자 확인: 11·13은 확정, 나머지는 임시안 수용)

1. **SW 스크립트 위치 미정**: §3은 앱 자산을 전부 `/__app/`에 두라고 하지만 스코프 `/`를 얻으려면 SW는 루트에 있거나 `Service-Worker-Allowed` 헤더가 필요하다. 계획은 `/sw.js`로 둔다(SW 스크립트 요청은 fetch 이벤트를 타지 않아 문서 경로와 충돌하지 않음).
2. **`outside-root`가 `..`로는 발생하지 않음**(§5.3-3, §9.2): 브라우저가 URL의 `..`를 SW에 오기 전에 해석한다. `../x.css`는 `/book/x.css`로, `../../x.css`는 `/x.css`로 도착한다. 계획은 "book 맥락 요청이 `/book/<존재하지 않는 id>/…`를 향하면 `outside-root`"로 기록하고, 루트까지 올라간 경우는 루트 절대경로와 구분할 수 없어 `missing`(또는 우연히 일치)으로 처리한다.
3. **페이지별 `<title>` 저장 위치 없음**: §6.2 파일 패널은 각 페이지 `<title>`을 보여주지만 §4.2에 필드가 없다. 계획은 `bookFiles`에 `titles: Record<path, string>`을 추가한다.
4. **파일 패널 머리의 `q3-report.zip`**: `sourceName`은 확장자를 뺀 값이라 `.zip`을 표시할 수 없다. 계획은 `sourceName`만 표시한다.
5. **`7 / 12쪽 · 62%`의 62%가 무엇인지 불명확**: 계획은 문서 전체 진행률(패널의 "전체 62%"와 같은 값)로 두고, 진행 바는 스펙대로 현재 페이지 %.
6. **모바일/PC 레이아웃 경계 미정**: 계획은 뷰포트 폭 768px 이상을 PC 레이아웃으로 본다.
7. **meta charset 없는 EUC-KR HTML의 응답 인코딩**: 가져오기는 EUC-KR로 판정하지만 브라우저는 Content-Type에 charset이 없으면 다르게 추측할 수 있다. 계획은 판정 근거가 BOM·meta가 아닐 때만 `text/html; charset=<판정값>`으로 저장한다.
8. **CSP 메타가 agent를 막는 경우가 드묾**(§5.4, 픽스처 13): agent는 `<head>` 직후에 들어가므로 뒤에 오는 CSP 메타보다 먼저 실행된다. 차단은 주입 위치가 CSP 메타 뒤로 밀릴 때(1024바이트 charset 보호 규칙)만 생긴다. 픽스처 13은 그 배치로 만든다. 제한 모드는 그대로 구현한다.
9. **재가져오기 시 `issues` 정리 기준**(§7.2): `missing` 기록은 원래 묶음에 없는 경로라 "사라진 경로" 기준이 맞지 않는다. 계획은 교체 시 그 문서의 `issues`를 모두 지운다.
10. **이어 읽기 복원 범위 미정**: 계획은 문서를 열 때의 첫 로드에만 `lastScrollRatio`를 복원하고, 문서 안 링크 이동·파일 패널·이전/다음은 맨 위에서 시작한다(`#hash` 링크를 깨지 않기 위해).
11. **[확정] 글꼴**: 사용자 결정으로 Pretendard를 번들한다. 원본 Pretendard v1.3.9 배포본의 `web/variable/woff2/PretendardVariable.woff2`(약 2MB)와 `LICENSE.txt`(OFL)를 `public/__app/fonts/`에 복사한다(P1 Task 14). `@fontsource` 패키지는 쓰지 않는다.
12. **`Space` 단축키**: 문서의 기본 스크롤 키와 겹친다. 계획은 기본 동작을 막지 않고 토글만 추가한다(모바일 레이아웃 한정이라 영향 작음).
13. **[확정 — 사용자 결정: PC는 상시 표시] PC 레이아웃과 "문서 공간을 차지하지 않는다"의 충돌**: §6.1·성공 기준 4는 리더 UI가 레이아웃을 밀지 않는다고 하지만, §6.2 PC 레이아웃은 상단 바 하나 + 폭 조절·접기 상태를 저장하는 우측 사이드 패널이고 `Space`(오버레이 토글)는 모바일 레이아웃 한정이다. 계획은 PC에서 상단 바를 항상 표시하고 패널을 도킹(iframe 폭 축소)하며, 책갈피 탭·하단 바·스크롤 핸들·첫 실행 안내·하단 진행선은 모바일 레이아웃에만 둔다.
14. **같은 `sourceName` 문서가 여러 개일 때 교체 대상 미정**(§7.2): "새 문서로 추가"를 고른 뒤 다시 가져오면 후보가 둘 이상이다. 계획은 가장 최근에 가져온 문서를 대상으로 하고 대화상자에 그 문서명을 표시한다.
15. **검색 결과 범위**: §4.3-6은 HTML 파일마다 평문을 만든다고 하지만 조각 HTML은 페이지가 아니다. 계획은 색인은 모든 HTML에 만들되 검색 결과에는 `pagePaths`의 페이지만 보여준다.
